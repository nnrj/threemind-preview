# E67: why /4 is slow — read-only review of existing evidence

October 12, 2026. Both `/4` arms remain deferred under the user's decision. This review reads earlier preflight/partial teaching files and source; it creates no engine and advances no simulation. Evidence is `analysis/deferred-4-performance.json` in managed storage, generated by [performance_review.py](performance_review.py).

**The current `/4` implementation is substantially slower inside native advancement under this dense sensory workload. Database access, video rendering and overnight chat inactivity do not explain that measured difference.** Function-level CPU attribution has not been profiled, so no percentage is assigned to individual functions. The overnight failure to launch is a separate execution omission and is not included as computation.

Three whole saves total about 18.075 seconds. Its 384 nodes and 139,380 directed edges have 94.77% density. Counters show 86,608,801 node-settlement visits, 386,595,620 edge-settlement visits and 142,017 expiry checks. The existing `scan_visits` counter is zero, which does not mean that all traversal or bookkeeping costs disappear. Pending state has 345 events and 139,917 local deadlines. Original clips extend through lesson 65; the complete restorable checkpoint remains lesson 48.

Local processing can still touch almost the whole dense graph and revisit the same object many times at one timestamp. That is the distinction between locality and low total work.

## Source findings

1. `advance_impl` settles/clones/writes a receiver for each inhibitory message. Many senders reaching one receiver at the same time repeat this work. About 953,000 node visits already occur in the surviving preflight branch, and 86.6 million in the 72-second formal checkpoint. The repeated path is established; its CPU percentage is not.
2. `receive` builds a recipient cohort for each actual packet, and `associate` checks ordered pairs within that cohort. A k-recipient packet produces approximately k² candidates, repeated for many packets in a dense graph. Simply skipping these opportunities changes learning rather than transparently optimizing it.
3. Internal events are encoded into JSON values and cloned/decoded on delivery. Settlement clones structs, updates maps and parses string timestamps; deadline changes remove and reinsert ordered-index entries. These are confirmed implementation costs, without measured per-function attribution.
4. The stability option schedules discrete per-edge updates at the propagation interval. The previous preflight records roughly 1.29 million expiry checks against 0.11 million for adaptive half-life, but similar advancement times. Counts alone cannot rank full-course speed, and the formal stability arm was never born.

## Recommendations and limits

Prioritize potentially equivalent changes: typed internal events, fewer copies/string conversions, avoiding unchanged deadline reordering, and fewer repeated settlements of one receiver at the same timestamp after proving identical event and floating-point accumulation order. Verify discrete decisions, whole-state restoration, fixed-input trajectories and backend agreement for each change.

Research changes to learning-pair generation and actual transmission density separately. Fewer pair opportunities, altered propagation periods, dropped signals or computation quotas change dynamics and require an approved kernel subversion and a new comparison. None is implemented in this study.

The current implementation is computationally unattractive for this workload. **Its shape/color accuracy is unknown because teaching/testing was deferred.** Completed `/2` and `/3.1` behavior and performance belong in the final report, not an extrapolation from this engineering review.
