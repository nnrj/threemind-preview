## 结论

**慢不是“局部机制天然无效”的证据，也不能仅用保存了更多连接来解释。实现中既有可以取消的重复工作，又有超出等价执行重构的学习规则变化。**

1. `/3.1` 是旧求解框架加局部保持与回收。全节点衰减、批量传播及全边资格迹/稳定度处理仍在；新增的保持结算和失效预约叠加在这些路径上。它没有完成“全部全图工作被局部事件替代”。
2. `/4` 默认运行路径没有发现每步全图刷新或重建全部索引。但内部信号包的所有有效接收者又被两两配对学习，和 `/2`、`/3.1` 的默认规则不同。高连接度下，这项工作最坏按节点数的三次方增长。
3. `/4` 同刻重复结算、对象克隆、JSON 往返、字符串时间、反复重排期限索引，把单次局部访问做得很重。稳定度选项还保留每条边每100ms的离散更新，只是分散成大量局部到期事件。
4. 旧局部性验收只证明加入无关孤立节点不会增加局部事件访问量，没有覆盖局部邻域很大、很多节点同时活跃时的组合放大。这是此前性能验证的缺口。

## 二、/3.1 为什么慢于 /2

### 2.1 只替换了部分全图工作

`ContinuousEngine::new_retention31`仍创建旧连续引擎再附加保持算子。运行中保留：

- `restoration.rs::relax`：按原事件/求解时刻遍历全部节点，处理激活、迹和抑制衰减。
- `lib.rs::advance_impl`：构造全节点激活基线，生成抑制。
- `continuous.rs::emit_continuous`：全节点排序、复制节点与邻接、传播后全边更新资格迹和稳定度、清理各节点直接/联想读数。

确实已局部化的部分包括权重按需保持、到期回收、删边及相关索引更新；旧全图 prune 和保持状态同步已不走。准确描述是“部分局部化”，不能说完全没有实现，也不能说全部完成。

### 2.2 每次边使用附带多轮期限预约

同一条边实际传导时，先更新 H 并预约失效；紧接普通权重强化后又重新预约。中间没有执行失效事件，第一次预约马上被第二次覆盖。

`retention.rs::timer`即使新旧期限完全相同，也会从 BTreeMap/BTreeSet 删除，再分别插入。`edge_changed`对成熟边的每次普通强化，还重复进行两端孤立标记/节点计时器清理。

E68 `/3.1` 最终原件中的运行计数为：

- 边保持实际结算 **3,357,181,044次**。
- 节点保持结算13,586,125次；失效检查564,604次。
- 最终存活边 touches 合计 **2,445,808,123次**。两条增加 touches 的学习路径随后都调用 `edge_changed`，因而仅这些存活边就支持至少24.46亿次相应失效预约调用；还未计删去的边及发射时另一轮预约。

这不是额外“记忆效果”的证明，而是同一学习经历产生的实现工作量。`/2` 存活边 touches 反而更多（2,607,331,469），不能简单解释为 `/3.1` 普通学习次数更多。

### 2.3 数据结构和公式重复

保持状态通过 BTreeMap 存在旁表，实际边另在 Vec/HashMap；一次操作反复跨多个索引。已经在当前时间结算过的边，在预约时仍计算一次 dt=0 的保持投影；H 增益中配置常量的对数反复计算。

还有一个确定的无效查询：全边尾扫先执行 `traversed.contains`，再判断是否启用旧稳定度遗忘。默认半衰期模式下后者始终不成立，前面的树查询完全无用。先判断模式即可跳过，不需要改公式。

H 增益、遗忘和阈值时间采用已约定的指数/对数及解析逆函数，**不存在阈值二分搜索**。公式本身不是无依据的错误；问题在重复计算频率和对象管理。

## 三、/4 为什么更慢，哪里偏离了预期

### 3.1 一次发送变成接收者之间的配对学习

源码链：`local.rs::emit`打包一个源的出邻居；`receive`按包身份汇集有效接收者；`associate`对这些接收者做双重循环。

例如 A 发信号给 B、C、D。除了 B、C、D各自处理信号，还会形成 B↔C、B↔D、C↔D 的候选强化或建边。默认统一接收让内部信号也进入此路径。旧 `/2`、`/3.1` 默认 `co-stimulus` 的内部信号不这样调用 associate。

因此，“外部和内部接收一致”在这里不只是统一节点响应，还扩大了关联学习机会。它被写入 `/4` 的实现/契约，但不能被描述成只改执行方式、不改学习过程。此前应当把这一变化及其复杂度单独说明和验证。

一包有 k 个有效接收者，就遍历 k² 次（含排除的自配对）；整轮为 `Σ k包²`。许多节点各自向稠密邻域发送时，最坏达到 O(N³)，而沿既有连接传递一次是 O(E)。实际门控会缩小接收集合，最坏上界不冒充正式实验实际次数。

这满足“只访问本包相关对象”的宽泛局部性，**不等同于节点只对自己实际收到的信号作出响应、再通过实际接触作用于别人**。它是本次最应重新确认的机制选择。

### 3.2 同时到达被重复投影

抑制包按来源拆开；每条抑制消息都调用 `settle_node`，即便接收节点已经在同一时刻结算过，仍克隆节点、解析时间、执行衰减表达式并写回。接收上下文计算先 settle，随后 touch 又 settle；出边和入射邻接也会重复结算同一条边。

第一轮纠错的既存计数增量：

| 计数 | /3.1 | /4 半衰期 | /4 稳定度 |
|---|---:|---:|---:|
| 节点结算/访问 | 2545524 | 403280120 | 411292996 |
| 边结算/访问 | 658869134 | 2185434581 | 2694290996 |
| 失效检查 | 150094 | 756504 | 419381205 |

这些版本的计数口径不同，不可直接当CPU耗时比例，但明确显示实际工作已达到数亿至数十亿次。

### 3.3 “局部定时”并未减少稳定度的周期工作

稳定度选项仍要求每条边在100ms格点进行原离散更新。它没有全边 for 循环，却为每条边弹出、执行、再插入期限。高连接度下，原先一次顺序遍历的工作变成 E 次有序队列操作，缓存和常数开销更差。4.19亿次阶段内到期检查与此一致。

这也是只把 H 改成稳定度不能解决慢的原因：共有的配对和对象成本还在，稳定度又多了一类周期事件。

### 3.4 局部对象过重，且还有无效邻接访问

- 内部事件先编码成 JSON Value，到达时 clone 并解码；这不是对外保存格式的必需开销。
- 节点/边克隆后再次克隆写回；内部时间字符串来回解析/创建。
- `timer`新旧期限相同时仍重排双索引。
- 每次 touch 扫 incident 边检查新颖窗口，即使多数边早已过窗。
- emit 先整理全部入射边抑制权重，再检查是否确需传导；同一源的 features 按出边重复生成。
- 每个节点/连接自己算衰减，比旧版同一步共享一份衰减因子多了数值运算。这一部分可通过纯函数缓存减少，不应偷偷改变衰减规律。

### 3.5 没有发现的原因

默认 `/4` advance 从事件/期限队列取下一时刻，未发现热路径全图快照或全图索引重建。全图投影主要在观察、图像、统计和保存；这仍有优化空间，但不足以解释原生推进中的主要差距。

`scan_visits=0`只表示显式scan-control分支没有扫描，不代表总访问量低。`pending_events`在 `/4` 包括期限项：H组141099由363消息加140736期限组成；不能拿它和旧版的2条传导队列直接相除。

四组使用同一 release 原生二进制（SHA-256 `baa17c4f150ada52b5b504286e801fe472f1695a3ff12b32be95b24c7cba9379`）；不是 `/4` 用了 Debug，也没有同时跑 Python 来同步。能量、休眠/唤醒、全局 homeostasis 在本批关闭，不能列作主因。全内部事件追踪亦未开启。

## 五、可执行的解决顺序与边界

| 优先级 | 处理 | 是否需要改变机制 |
|---|---|---|
| P0 | 不变期限不重排；先判模式跳过无效查询；一次发射结束只预约一次最终期限 | 可作等价实现优化，须验证完整状态和顺序 |
| P1 | 内部有类型消息、整数时间、减少克隆、就地更新、缓存常量和源特征 | 可作等价实现优化，保存格式仍兼容 |
| P1 | 同刻已结算值复用；仅维护待新颖结算的邻接；抑制路径提前门控 | 保留所有阈值裁限、累加顺序、审计口径及失效时间后验证；不能随意跳过状态写回 |
| P2 | 重定内部信号应产生哪些建边/强化机会，取消不合意的接收者互配 | 实质学习规则改变，先确认并另立如 /4.1；旧 /4 保留 |
| P2 | 稳定度离散更新能否精确解析/合并，或接受新遗忘公式 | 精确等价才能沿用版本；否则另版本，不能直接改大内部步长 |

不能以降输入量、跳信号、强行限边、关闭学习、稀释教学、回退或加全局配额来冒充优化。普通宿主限速也不减少相同模拟经历所需的总工作。

建边规则若改为实际接触或本边收到的信号，还需明确“原本没有连接的对象如何首次接触”。不能为性能悄悄增加全局候选筛选、语义奖励或根据显示位置补连。保留消息顺序的底层批处理，不需要增加全局观察者来分配学习机会；模型局部规则与执行器的数据布局是两回事。

验收应覆盖：未受影响的孤立大图、固定节点数下不同连接度、同刻大量来源、连续密集感官输入；分别记录候选配对、有效学习、同刻重复结算、期限未变重排，以及推进/观察/保存。校验输入、事件顺序、删除时刻、完整状态、恢复和Python/Rust一致性。仅“扫描计数为0”不再作为充分验收。
