# 连续采集积压修复（2026-09-09）

## 原因与决定

旧路径除了先保存采集原件，还会在 worker 处理每个采集块时强制同步保存整个意识。默认每秒五块音频由此变成频繁的全模型检查点。检查点写连接表时持有排他行锁，确认请求也等待这把锁；千节点、数万连接时，几秒的等待就可能填满默认 16 块队列。

连续采集现在复用 `checkpoint_us` 指定的正常提交节律，以及既有的物理时间、内存缓冲、停止等提交条件。原件、编码器状态、序号和输入命令仍先原子入库；调度与递送记录、命令游标与 Core 状态仍在同一次检查点中提交。恢复从已提交游标继续处理，不把“接收确认”冒充“已经递送”。普通手动文字输入、显式保存和器官开关仍可及时请求检查点。

检查点使用 `FOR NO KEY UPDATE` 锁住意识行，连续输入使用 `FOR KEY SHARE`，二者可并行，仍禁止意识在采集中被删除或更换身份。普通输入的 `FOR UPDATE` 与连续输入互斥；多个连续输入再使用按意识划分的事务建议锁串行检查预算与序号。锁顺序始终是意识行在前。采集鉴权与查询也移出异步事件循环，数据库等待不再卡住其他请求和输出流。

没有更改 Core、采样频率、编码规则、帧时间或队列上限，也没有丢弃采样来掩盖积压。接收时按当时可见的已提交意识状态校验；若与暂停、关闭或死亡并发，原件被接收不保证最终递送，最终结果以检查点输入审计为准。

## 界面与限制

聊天区耳朵／眼睛旁直接显示已确认数、待确认数／上限和最近确认耗时；溢出提示包含这些数值和设置入口。上限在「参数配置 → 高级参数 → 连续设备采集 → 客户端待确认块上限」，仍默认 16，可设置 1–256。持续超载仍会明确停止采集，不能用更大队列解决无限增长。

## 验证

`tests_v2/test_live_media.py` 覆盖并发重试只接收一次、检查点事务仍在写入时可确认采集块、按正常节律提交的完整递送审计、异步接收线程隔离、暂停恢复与原件导出。`threemind-ui/e2e/capture-throughput.spec.ts` 用虚拟麦克风覆盖空白、默认物理环境以及 1,024 节点／64,512 初始连接网络下同时开启耳朵和嘴巴的持续操作。

逐步减少检查点次数的中间实现仍在大网络下溢出，不能单独视为已修复；最终并行入库方案通过大网络复测。各轮时延属于本机工程观察，受后台负载影响，不用于精确速度比结论。这些是工程验收，不是意识研究结果，也不保证所有规模都能实时运行。后续实验保持当前 `threemind.causal/9` 动力学。
