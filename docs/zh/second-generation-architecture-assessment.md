## 1. 结论与用户约束

建议定位为：**共享同一内核的 ThreeMind Runtime 与 ThreeMind Lab，分别服务于设备运行与训练研究；Lab 同时支持本地工作站和在线多用户部署**。

Lab 第一版以 PostgreSQL 为唯一持久化主存储，工作站连接本机数据库，在线部署连接服务器数据库；PostgreSQL 并不意味着云端依赖。Core 在内存中演化，不依赖数据库、文件系统、账号系统或消息代理。Runtime 可选轻量 SQLite 恢复库，也可纯内存运行。模型文件用于用户按需导出、交换和导入，不作为持续更新的运行状态副本。

用户已明确的约束：

- 保留匿名内核、刺激驱动的局部连接生成与可塑性、先天模型的环境训练来源，不能人为植入语义节点、任务答案或指定脑区。
- 默认拓扑驱动；前端布局不参与内核因果。空间机制是独立的可选实验条件。
- 采用明确模拟时间和时间戳事件的新内核，验证后直接切换主线。旧内核及旧数据兼容不能约束新设计。
- 旧 `data` 主要是测试数据，默认不迁移、不批量扫描，不投入人工阅读与转换成本。
- 网络呈现采用原生 Three.js；首先保持现有视觉与交互效果，再独立评估改进。
- 设置中允许手动选择高档位，不因设备配置较低而禁用选项。
- 增加文档菜单，首项为索引，正文来自项目 Markdown；专门介绍内核架构、原理、实现和公式。
- 未来开源并在服务器公开提供研究验证，因此第一版需建立身份、项目归属和任务隔离的基础。
- 用户取得代码后可以在本地部署完整工作站，不依赖云端存储或在线账号。
- 训练/开发/研究工具和模型部署运行时需要分发边界；部署后的模型仍然按照相同规律保持可塑性。

本机 PostgreSQL 17 位于端口 5433；已按用户提供的配置创建专用 `threemind` 数据库与角色。没有修改 poemhaven/daydream 的业务数据库。

## 2. 当前问题与研究判断

ThreeMind 值得作为可塑动力学和具身学习研究继续推进，但目前没有充分证据证明已实现主观意识、通用推理或相对于简单循环可塑网络的稳定优势。

本轮新版 UI 验收中的一个 30 秒持续物理输入样本形成了 12 个节点、120 条有向边，总激活达到 12（节点激活上限为 1）。这是值得优先检查的高密度、饱和状态，不能解读为认知能力增强。该样本尚不能判定是否存在病态吸引子；下一轮应预先设计刺激撤除、感官通道相关性控制、稀疏刺激、扰动恢复和步长收敛对照，区分持续输入、编码方式与核心自维持动力学的贡献。工程性能改进不能替代这类机制验证。

需要优先区分内核效应、感官编码偏置、读出算法效应和研究者的视觉解释。主要已确认的问题包括：

- 主历史持久化以键对应整份 JSON，保存时重复复制、序列化和替换全部历史；换一个数据库品牌不能自动解决这一写法。
- `state_dict()` 中存在共享可变引用，运行中的配对分叉不能据此保证同一起点。
- 当前追踪窗口不能保证保存整个运行的证据，部分统计图表把未知值变成零。
- 全图输出复制、锁内全历史复制、无界观察队列以及过大的前端更新范围会随运行规模增长放大开销。
- 生命周期混合了模型活动、无响应、人工停止和执行故障，需要分离。
- 部分适配器随机源和宿主物理遥测使相同 seed 不等于相同实际输入。
- 实验、比较、消融、统计和证据导出尚未形成一致的完整工作流。

前轮检查中，内核、分析和时序读出的 74 项测试通过，前端生产构建通过；另两项实验测试受临时目录权限影响，未计入通过数。合成微基准显示，5,000 节点、50,000 边的一次推进，在空间机制关闭时约 648 ms、开启时约 2,004 ms；这不是实际长期运行的容量承诺。不能把卡顿简单归因于显卡。

## 3. 四种模型相关对象

| 对象 | 性质 | 职责 |
| --- | --- | --- |
| ModelSpec / ModelState | 明确版本的模型定义与可序列化状态 | 定义拓扑、权重、快慢状态、规则、感官映射和内核随机状态 |
| RuntimeModel | 内存中的可变运行实例 | 接收刺激、传播活动、形成和改变连接；由单个 worker 拥有写入权 |
| DatabaseCheckpoint | 数据库中的不可变恢复点 | 保存某个因果边界上的完整状态及已提交序号；实验恢复还包含适配器、输入队列与模拟环境状态 |
| ModelArtifact | 用户按需导出的模型文件 | 交换、独立运行、归档或导入平台；文件内容不可变 |

初始模型版本不随运行覆盖。学习发生在 RuntimeModel 中；用户需要把学习结果作为新起点时，从指定状态创建一个有谱系的新模型版本。

数据库中的恢复检查点可以自动保存。这不等于自动导出模型文件：前者服务于恢复和审计，后者是用户请求的交换产物。运行结束时提交最终状态到数据库，不自动生成或改写 `.tmind` 文件。

## 4. 内核边界与运行方式

### 4.1 一个内核、两个产品、三种使用场景

| 层/产品 | 所含能力 | 部署与持久化 |
| --- | --- | --- |
| ThreeMind Core | 动力学、事件处理、状态捕获与恢复 | 嵌入式库；不依赖任何数据库或 Web 平台 |
| ThreeMind Runtime | Core、时钟策略、感官/身体适配器、模型编解码、CLI/SDK | 可独立安装到电脑或机器人；纯内存或可选 SQLite 本地恢复库；无需 Lab、PostgreSQL 或在线账号 |
| ThreeMind Lab Workstation | Runtime worker、训练环境、实验、比较、统计、证据、文档和模型管理 | 本机应用及本机 PostgreSQL；本地单用户身份，完整本地使用 |
| ThreeMind Lab Server | 同一套 Lab，加多用户登录、项目权限、配额、公开资源与管理区域 | 部署者控制的服务器及 PostgreSQL，可调度多个 worker |

Lab Workstation 和 Lab Server 是同一个产品的两个部署配置，不维护两套前端和业务实现。Runtime 与 Lab 有独立安装包和依赖边界；统计库、Web UI、训练环境和身份系统不能成为 Runtime 的强制依赖。训练用 worker 复用同一 Runtime，避免“研究内核”和“部署内核”逐渐变成不同机制。

训练器是 Lab 的编排模块：准备环境与初态、执行训练协议、调度运行、记录观察、评估结果和创建有谱系的模型版本；具体动力学与连接塑造始终在 Runtime 中发生。Lab 还包含训练器之外的开发、比较、消融、统计与文档工具，所以产品名采用 Lab。

这类似开发工具链与运行环境的划分，但不能照搬“训练时学习、部署时只推理”的含义。可塑性属于 Core；Runtime 默认继续受环境塑造。关闭可塑性只能是明确记录的实验/部署条件，不是分发为 Runtime 时自动发生的改变。

本地工作站默认所有必需服务和数据库都在本机。远程 worker 是可选算力：只有使用时才传递相应模型和输入；工作站可主动连接远端并收取结果写回本地数据库，不要求开放本机 PostgreSQL 端口。选用远端算力意味着相应状态会在远端处理，但不把工作站的主数据迁往云端。

### 4.2 内核接口与计算

推荐 Python 科学参考实现、Rust 高性能实现、PyO3/maturin 连接 Python 科研生态。先实现新时间语义的可读参考内核，再验证 Rust 实现；不要求先完整移植旧内核。

部署用 Runtime 优先提供 Rust 原生库和 CLI，Python 绑定为可选接口，不要求机器人为了运行模型安装完整 Python 科研环境。设备适配器独立分发；桌面、Linux 服务器及 ARM64 设备逐项验证支持，不能以能编译代替实际平台验证。

核心接口围绕以下能力组织：

```text
Engine(ModelSpec, ModelState)
inject(StimulusEvent)
advance_to(simulation_time)
capture_state() -> ImmutableStateImage
restore_state(ImmutableStateImage)
```

Engine 不持有数据库连接，不接收文件路径，不调用账号、网络服务或渲染器。文件读写由 ArtifactCodec 和 CLI/宿主完成；数据库访问由平台持久化层完成。

支持两类内核宿主方式：

1. 平台运行：数据库恢复状态 → worker 构造 RuntimeModel → 内存演化 → 宿主批量持久化到 PostgreSQL。
2. 独立 Runtime：CLI/SDK 解码模型文件或接收内存状态 → Engine 演化；不需要 PostgreSQL、Web 服务或登录。纯内存模式不保存；需要设备断电/重启后延续学习时，显式启用本地 SQLite 恢复模式。

Runtime 的 SQLite 适配器只负责实例身份、状态分块、提交序号和所选恢复日志，不包含 Lab 的用户、实验、统计和分布式作业 schema。它和 PostgreSQL 共享 ModelState/Checkpoint 的逻辑协议与编解码器，而不是共享一份不断双写的数据库。

开始新实例、恢复已有实例、导入新模型使用明确的不同操作。原始 `.tmind` 只作为输入；后续变化写入启用的本地恢复库，不覆盖原始文件。使用者不选择持久化时，应明确显示重启不会自动保留未导出的学习结果。

内核使用连续字段数组、稳定标识和动态稀疏邻接索引。数据库中的图表不能代替内存邻接结构参与每个微步的传播。优先并行多个独立实验，不在第一版把同一意识的节点分散到多机通过消息逐跳传播。

观察读取不能直接改写内核。真实宿主负载经传感器进入网络属于环境因果链；严格的无 UI/有 UI 性能和行为比较使用固定记录输入。

## 5. 时间、生命周期与物理闭环

新内核分离模拟时间、宿主单调时间、输入序号和数值步数。保留感官事件边界，按时间戳及持久化顺序递送，不因为感官帧数量增加而自动增加同一时间段的演化时长。

提供实时、指定倍率、尽速训练三个宿主调度模式。实时模式锚定操作系统单调时钟；CPU 负载、温度和频率可作为感官输入，不默认作为模型时间的速率控制器。

加速模式要求环境、感官与动作后果共同使用模拟时间轴；不能只增大时间戳、跳过动力学。长期模拟的时间表示应避免绝对浮点时间精度损失和单个 64 位纳秒计数器的范围限制。

分别规定衰减、传播、抑制、巩固、遗忘的时间尺度与数值方法。简单衰减可使用时间常数，非线性项不能统一乘倍率后直接宣称等价。时间步长是数值协议的一部分，不能由显示性能档静默调整。

执行状态与模型生命状态分开。暂停、资源阻塞、崩溃、人工终止、稳定平衡和暂时无响应不等于死亡。首次有效刺激前为待刺激；有效输入停止且内部活动及可继续产生活动的待传播事件耗尽时，才满足约定的死亡条件。

首期计划增加 MuJoCo 简化平面身体环境和单个发育训练流程。匿名输出经版本化身体映射产生物理作用，再由感官返回；不向内核注入语义目标或任务答案。复杂三维世界和种群演化后置。

先天版本保存训练环境、感官映射、祖先校验和、选择标准和形成时间。继承出生与精确恢复使用不同入口；出生的快状态重置规则明确记录。

## 6. PostgreSQL 是 Lab 唯一持久化主存储

### 6.1 本地部署、多用户部署与 SQLite 的边界

多后端可实现，但不同的锁、任务领取、分区、权限、类型和迁移行为都需要单独实现与测试。ORM 只能减少部分语法差异，不能消除这些语义差异。

在个人单机条件下 SQLite 合理；加入多机 worker、多用户中心服务的方向后，PostgreSQL 更适合作为 Lab 的第一版统一后端。本地 Lab 使用本机 PostgreSQL，与线上 Lab 使用相同 schema 和迁移链；不需要云端存储，也不因为启用了 PostgreSQL 就必须出现登录页。

Runtime 的轻量 SQLite 恢复库随其可选持久化功能提供。第一版不承诺把整个 Lab 原样移植到 SQLite；如未来需要一个无需 PostgreSQL 的完整轻量工作站版，再评估该适配器。每个工作站/在线 Lab/独立 Runtime 都有明确的单一主存储，不同时双写两个权威副本。

SQLite WAL 是 SQLite 的写前日志模式，不是另一种数据库。事务先追加日志，再由 checkpoint 合并回主数据库；允许读写并行，但仍然只有一个同时写入者，不适合把同一数据库文件放在网络文件系统上供多机并发使用。启用 WAL 不等于不再读写文件，也不等于无需考虑提交持久性、检查点和备份。设备恢复库采用经维护的 SQLite 版本与明确的同步策略。

跨环境交换有三类明确路径：

- 本地 Lab → 在线 Lab：相同数据库 schema，可通过项目级导出/导入或受控数据库迁移工具完成；公开项目不携带本地会话、密码和数据库账号。
- Runtime → Lab：按统一检查点/模型协议导入，SQLite 和 PostgreSQL 的内部表结构不需要一致。
- Lab → Runtime：按需导出标准模型；Runtime 解码后创建新实例或按明确恢复操作继续。

两个同源实例独立经历刺激后属于两个演化分支。可以保留谱系、比较并选择其中一个状态，但不能用“数据库同步”静默合并为一个意识。初始测试数据仍不迁移。

### 6.2 数据分层均在 PostgreSQL 中实现

| 逻辑层 | 内容 | 写入和查询方式 |
| --- | --- | --- |
| 项目与模型目录 | 用户、项目、协议、运行、模型版本、谱系、产物索引 | 结构化关系表、外键、索引和事务 |
| 当前状态投影 | 节点、边及可筛选的当前属性 | 批量增量更新；每个可见版本标记一致的状态序号 |
| 因果事件 | 实际递送输入、参数变更、干预、拓扑事件、执行异常 | 追加写入，按运行和序号检索 |
| 动力学观测 | 指标、节点/边轨迹、采集覆盖信息 | 批量追加、按运行和时间范围查询；高容量数据进行分区 |
| 恢复检查点 | 状态元数据、校验、快慢状态和环境状态分块 | 不可变检查点记录及有界二进制块，不持续替换单个无限增长 JSON |
| 平台作业 | 领取、租约、尝试、进度、结果、审计和 outbox | 短事务、幂等提交和失败恢复 |

可筛选的节点和边有结构化投影，不能只把整个模型塞进一个 BYTEA 后称为可查询数据库。恢复点中的二进制块用于快速恢复，结构化投影用于条件筛选，两者关联到明确状态边界。

普通对象操作使用 SQLAlchemy 与 Alembic；高吞吐批量写入使用 Psycopg 3 的 COPY/批量语句，避免为每个数值构造一个 ORM 对象或单独提交事务。采用 PostgreSQL 支持的分区、索引和事务快照；不预先维护所有数据库方言。

Lab 的大块原始媒体和检查点也通过分块 BYTEA 持久化，第一版不自动外置 Parquet 或对象存储。必须实测数据库体积、WAL、备份和恢复成本。未来若原始媒体规模证明外置对象存储有明显收益，再单独修改该决策，不能静默增加第二份权威存储。Runtime 的本地恢复库采用有界分块和必要索引，不照搬完整研究历史。

### 6.3 保持精确性，避免用数据库替代数值计算

连接的生成、删除及干预必须有可审计记录；连续权重和激活变化具有两种明确的采集方式：

- 标准可重放记录：完整内核输入与外部操作、完整恢复状态、关键结构事件、周期观测；需要更细历史时从数据库检查点及事件重放得到。
- 详细追踪：额外持久化指定变量在规定数值边界的完整增量，用于必须直接检查轨迹的研究。

采集协议与显示性能档独立。不能因机器慢而暗中降低记录精度；若输入或恢复信息不足，明确标记不能精确重建。详细追踪的存储吞吐本身会限制训练速度，不能承诺无限记录与无限加速兼得。

历史条件查询绑定时间范围和状态版本。已有投影可以直接查；需要尚未物化的历史状态时，创建后台重建任务后在数据库中查询结果，界面显示重建进度和数据质量。

### 6.4 内存最新状态与已提交状态

RuntimeModel 是当前执行状态，PostgreSQL 是已经提交的持久状态。批量异步写入期间，两者可能相差一个有限窗口，必须显示各自的序号和模拟时间。

采用有界缓冲、批量提交和幂等批次标识。数据库不可用或积压达到预算时，模拟运行在因果边界进入资源阻塞；真实感官无法暂停世界时，记录中断/缺口，不能伪称全部保存，也不能把记录器故障判定为模型死亡。

恢复只承诺恢复到已提交的证据边界；没有提交的进程内状态不能宣称在崩溃后仍然存在。

## 7. Arrow、日志与导出格式的修订

### 7.1 Arrow 保留为批量表示和二进制编码

Arrow RecordBatch 不是数据库。它用于 Rust/Python/传输之间的有类型列式批次，以及状态二进制编码；能够减少对象转换，但不宣称整个链路都零复制。

本版不把 Arrow IPC 文件作为自动持久化主日志，不常驻另一套 DuckDB 主库，不自动将实验记录转存 Parquet。Parquet 可以作为用户请求的分析数据导出格式；DuckDB 可以是独立研究者分析导出数据的工具，均不是平台运行必需组件。

### 7.2 两种日志不能混淆

- PostgreSQL WAL：数据库自己维护的崩溃恢复日志，不由 ThreeMind 重写一套。
- 研究因果日志：ThreeMind 在数据库表中记录刺激、时序、干预与变化，服务于实验解释和重放。

数据库 WAL 不能替代有研究语义的事件日志；反过来，研究日志也不替代数据库事务和备份。

### 7.3 模型规范和用户导出

规范首先定义独立于存储媒介的 ModelState schema，格式版本、动力学版本和采集协议版本分别管理。

推荐标准交换文件为 `.tmind`：ZIP 容器内放版本化 manifest、列式二进制状态块和校验清单。状态块采用 Arrow IPC，需要压缩时采用无损压缩，避免同一内容重复压缩。这个二进制文件是数据，不包含可执行的模型脚本。

JSON 是同一逻辑状态的可读表示；大整数、浮点数及类型有明确的无损规则。状态哈希根据规范化逻辑状态计算，另有文件字节校验和；ZIP 时间戳等容器差异不能伪装成模型差异。

UI 分开提供：

1. 标准模型导出：完整 `.tmind`，用于独立运行或重新导入。
2. JSON 模型导出：相同覆盖范围的可读状态表示，可无损导回。
3. 数据/证据导出：当前筛选结果、历史、CSV/JSONL/Parquet、图表和复现说明；ZIP 可包含完整模型及配套证据。

ZIP 是容器，不另定义第三套模型语义。筛选出来的部分节点/边属于数据或子图产物，不默认为可恢复的完整模型。

### 7.4 导出最新状态与导入恢复流程

```text
导出最新状态：
请求导出 → worker 在边界 S 冻结状态 → 将 S 提交为不可变数据库检查点
→ 导出器读取该检查点 → 用户下载文件

恢复运行：
选择数据库检查点 → 恢复已提交状态和所需事件 → 构造 RuntimeModel

导入运行：
校验模型文件 → 规范化并写入数据库 → 创建模型版本/运行 → 从数据库启动

独立运行：
调用者解码模型 → 内存 ModelState → Engine，完全不需要数据库
```

导出时不能在网络持续变化的情况下分别读取不同时间的节点和边。状态冻结之后允许运行继续；导出失败不修改原状态。运行中的原模型文件始终不会被自动覆盖。

## 8. MQ 与多机运行

第一版不引入独立 MQ。采用 PostgreSQL 作业表、短事务领取、租约、心跳、重试与幂等结果提交。使用 `FOR UPDATE SKIP LOCKED` 领取待处理任务；只在任务队列场景使用，不能用它规避研究查询的一致性。

为发布通知保留事务内 outbox。LISTEN/NOTIFY 可以唤醒消费者，但任务事实仍在表中，消费者重启后通过表恢复；通知不是持久消息队列。

每个运行同时只有一个有效 worker 写入。租约代次作为 fencing token，拒绝过期 worker 的迟到提交。交付按至少一次处理设计，依靠运行/批次唯一键与幂等事务避免重复生效，不宣称 MQ 提供端到端 exactly-once。

内核输入/输出总线仍然存在，使用进程内有界队列、IPC 和批量传输；不把每次神经传播拆成远程消息。

当实测表明多种消费者、复杂路由或跨机解耦需求超过数据库作业队列的合理边界时，再考虑独立 MQ。数据事件仍有数据库证据记录，代理不成为新的模型权威状态。

首期支持多 worker 执行不同运行；同一意识的跨机分布式数值计算后置。worker 通过认证控制/数据接口接入，不把数据库端口暴露给浏览器或公众。

## 9. 账号、权限与管理界面

Lab 第一版需要最小多用户基础，不必建设独立管理后台项目；Runtime 不依赖这套账号系统。

身份与权限分两层：平台管理员负责平台运行；项目 owner/researcher/viewer 负责研究资源。所有运行、模型、数据、导出、分析和 worker 任务都绑定项目。服务端 API、WebSocket、下载和后台作业均执行权限校验，不能只隐藏按钮。

推荐本地账号、成熟密码散列库和服务端会话作为在线 Lab 首期认证方式；初始管理员通过安装流程或 CLI 创建，公开注册默认关闭。工作站默认使用仅回环访问的本地身份模式，无在线账号、无云端登录，同样保留项目归属和会话边界；开放给局域网成员或互联网用户时必须切换认证模式，不能把本地自动身份直接暴露到网络。OIDC/机构单点登录后置。

数据库采用应用鉴权与 PostgreSQL RLS 共同保护项目边界；应用角色不是超级用户、表 owner 或 BYPASSRLS 角色。连接池中的项目上下文按事务设置与结束，测试跨请求上下文泄漏。

同一前端增加仅管理员可见的管理区域，提供：

- 用户启停、邀请及会话撤销；
- 项目成员与角色；
- worker 注册、状态、停用与任务管理；
- 并发/时长/存储配额；
- 关键操作审计与公开资源管理。

第一版不做独立后台代码库、自定义权限流程引擎、收费系统、复杂组织树或开放式任意代码执行服务。

公开发布采用分阶段能力：匿名访客可阅读明确发布的不可变研究/模型/证据；登录研究者可在授权项目中复算；共享计算服务在 worker 隔离、配额、限流和审计验收后开放。公开 worker 默认运行受控实验协议，不直接执行上传脚本、任意 SQL 或宿主命令。

公共服务器使用明确的模拟环境或获准的数据源；本机物理设备接入由对应专用 worker 配置。显示档位可自由选择，服务器任务配额属于另一个明确的调度边界。

## 10. 科研功能与 UI

工作流为：研究项目 → 协议 → 运行 → 比较/干预 → 统计分析 → 证据导出。

必须具备协议冻结、条件组、参数扫描、独立种子/环境区组、批量运行、原子分叉、匹配消融、恢复测试、因果事件时间轴、效应量、置信区间、置换检验、多重比较与缺失质量标记。

初始对照包含随机循环网络、简单 Hebbian 网络和关闭可塑性的 ThreeMind；其他基线按待验证主张加入。内核比较共享实际递送输入；适配器比较共享原始刺激；闭环实验共享环境初始条件和外生扰动，允许动作后果分化。

先形成保留/再触达、持续可塑性和目标结构消融三类决定性实验。探针也是刺激，使用只读量或分叉副本测量；独立运行、发现与验证数据分开，不能把同一确定性状态复制很多次当成很多独立样本。

前端保留 React/TypeScript/Vite，使用路由、查询缓存和虚拟列表；Radix 组件和统一样式变量。高频图状态由 Worker 和专用渲染仓库管理，React 不每帧复制整图。

Lab API 保留 Python/FastAPI，按项目权限、模型状态、实验作业、分析、导出和文档拆分业务模块。API 进程负责请求与订阅，不承担长期数值运行；Runtime worker 和分析 worker 独立执行作业。单机可以由一个启动器管理这些本地进程，多用户部署可以分别扩展，首期不拆成大量独立微服务。

原生 Three.js 实现批量点线、实例化和按需渲染。必须保留现有效果作视觉回归基线。ThreeJSON 当前已有动态批处理和按需渲染，不把它描述为必然的性能负担；本地 alpha.10 的关键批处理/帧循环与已安装 alpha.9 相同，尚无证据表明升级可以解决当前热点。

ECharts 负责交互图表，Python 科学计算库和 Matplotlib 负责统计与论文图输出。显示数据、导出表和论文图关联同一数据快照与分析版本。

新增文档菜单：索引、入门、核心假设、内核原理与公式、感官/身体/时间、实验/统计、模型/数据、部署/性能、研究记录与版本决策。借鉴 ThreeJSON Reader 的目录、主题、源码切换和链接处理，整合为 React 页面；资源本地打包，支持公式、Mermaid、搜索和离线阅读。正文来自受控 Markdown 清单，不扫描旧数据。

内核文档必须连接“原理—公式—符号/单位—更新顺序—实现位置—验证用例”，明确时间、归一化值、阈值和物理量的区别。

设置提供自动、轻量、标准、高档和自定义模式；手动选择不因设备等级被禁止，也不自动降档。显示质量、运行资源预算和科学采集协议分别管理。

## 11. 公共接口方向

API v2 显式包含项目、运行、状态版本和任务标识，取消依赖全局活动实例的写操作。

- StateStore：提交事件/批次、保存和恢复检查点、查询指定版本投影。
- ArtifactCodec：内存状态与标准二进制/JSON 的转换，无数据库和业务账号依赖。
- StudySpec/RunSpec/ArmSpec：协议、初始状态、条件、时钟策略、采集策略和资源要求。
- Job/Lease/Attempt：任务领取、有效所有者、进度、重试和幂等提交。
- QueryResult：数据快照、时间范围、分页游标、覆盖质量与持久化水位。
- ExportJob：模型或筛选数据的明确导出范围、格式、校验、结果状态。

长时间的历史重建、分析和导出全部作为后台任务。前端流具有基线快照、序号、断序恢复和订阅范围；观察帧可以合并，证据不能静默丢失。

## 12. 交付顺序与验收

1. 冻结旧 Git 基线与少量合成对照；写清新时间/状态/生命周期和 Core/Runtime/Lab 边界，不迁移旧测试数据。
2. 建立无数据库 Engine、StateStore、ArtifactCodec 及新参考实现，分发独立 Runtime；提供可选 SQLite 恢复适配器；建立 Lab PostgreSQL schema、项目身份和迁移链。
3. 打通 Lab 输入持久化、数据库恢复点、worker 租约、条件查询、按需导出/导入和一个端到端实验；验证本地工作站与在线配置共用业务实现。
4. 验证 Rust 内核、重建图渲染及实验/统计工作台、文档阅读器和最小管理区域。
5. 完成物理闭环、先天谱系、多机独立运行与长期稳定性验证；新内核通过后直接成为主线。
6. 先公开不可变研究成果与复现包，再按隔离和配额验收结果开放托管计算。

关键验收：

- 无 PostgreSQL、无网络的测试环境中，Engine 仍能从模型状态运行、学习和捕获状态。
- Runtime 最小安装不引入研究 UI、统计服务、账号或 PostgreSQL 依赖；默认可塑性与训练用 Runtime 一致。
- 工作站在所有云端服务不可达时仍能创建、训练、分析、保存和导出；可选外部模型服务不成为基础工作流依赖。
- SQLite Runtime 检查点导入 Lab、Lab 模型导入 Runtime 的逻辑状态和后续演化通过往返测试；两种存储没有隐式双向同步。
- 平台运行和结束不自动生成/改写模型交换文件；最新状态查看、恢复和导出均有明确数据库来源边界。
- 捕获状态后源运行继续演化，捕获结果不会被共享引用改变；分叉各组初态哈希一致。
- 二进制与 JSON 完整模型往返后逻辑状态一致；完整恢复还验证队列、随机状态、感官和模拟环境。
- 跨架构运行分别标明状态编解码一致性、数值容差内一致性和逐位确定性的支持范围；不能因为共享 Rust 源码就宣称所有 CPU 上逐位重放一致。真实设备恢复状态后重新接入当前环境，不能宣称外部物理世界一并恢复。
- 查询分页绑定一致状态，不混用不同 tick 的节点和边；部分数据不能假装完整模型。
- 批量提交重试不重复生效，过期 worker 不能写入；数据库或记录器故障不会被判定为模型死亡。
- 时间精度、子步收敛、事件顺序和加速/实时模式经过验证；旧内核行为差异被解释，不要求强行兼容。
- 用户不能通过替换项目、模型、导出或 WebSocket 标识访问其他私有项目；管理员边界、会话撤销、公开资源和配额有测试。
- 在 PostgreSQL 中对合成规模测试写入速率、提交延迟、WAL/表体积、查询、备份与恢复，不能只测 Python 对象操作速度。
- 固定图规模下进行 24 小时内存和队列稳定性测试，并分别测无 UI、有 UI、导出和并发分析；图自然生长的状态内存单独核算。
- 标准机性能目标为 10,000 节点/100,000 边固定基准、30 FPS 观察和常规界面交互 p95 延迟不超过 100 ms；它们是待测验收目标，不是当前性能结论，不包含后台导出和历史重建耗时。
