# 执行队列与部署额度

Lab 使用同一 PostgreSQL 内的任务队列。管理员可在“管理 → 执行队列与额度”统一调整并发，并为项目设置单独额度；项目成员在“设置 → 执行队列与额度”查看自己项目的状态。这些配置不进入模型文件，也不改变意识参数、模拟时间或显示性能档位。

## 三类执行队列

| 队列 | 任务范围 | 首次初始化默认并发 |
| --- | --- | --- |
| 实验与数据处理 `runtime` | 意识运行、受控研究计划、配对实验、分析、模型与数据导出 | 2 |
| AI 请求 `ai` | 已授权供应商请求及现有 AI 工具 | 2 |
| 通知邮件 `notification` | 已启用规则产生的后台邮件 | 1 |

每个队列独立计数。有效期内的租约占用并发；尚未领取的任务不占用，过期租约计入待恢复数量。过期不等于成功，也不代表模型死亡。

并发值支持 0～1024。0 暂停该范围的新任务领取；已经执行的任务继续续租、提交并正常结束。降低上限后，执行数可暂时大于新上限，待原任务退出后才恢复新领取。若要暂停具体意识，应使用该意识自己的暂停命令。

## 部署上限与项目额度

首次启动新版 API 或 CLI worker 时，从 `THREEMIND_MAX_ACTIVE_JOBS`、`THREEMIND_MAX_AI_JOBS`、`THREEMIND_MAX_NOTIFICATION_JOBS` 初始化数据库策略。之后以数据库中保存的策略为准，重启或启动不同配置的 worker 不会覆盖它。既有环境变量仍决定工作站启动多少个相应 worker 进程；数据库额度不负责创建进程。

项目的每个队列默认“继承部署上限”，JSON 为 `null`。填写整数则使用单独额度；有效值不高于部署上限，同时仍受整个部署当前占用约束。举例：部署允许 4 个运行任务，项目 A 的额度为 1，则 A 同时最多占一个运行位置，其他项目仍可使用余下位置。项目的 AI 和通知额度可独立继承或设置为 0。

项目达到额度时，调度器继续寻找其他可领取项目，不会将该项目排队当作整个队列阻塞。额度不是预留位置或严格轮询公平保证；未限制的项目仍可能使用全部空闲位置。受控计划在一个任务内执行步骤；配对实验的共同培养占一个任务，随后生成的各条件运行是独立任务，分别受并发额度约束。

这不是操作系统的 CPU、内存、磁盘硬配额，也不是任务吞吐保证。大模型的内存、科学容量限制、源采集设备、依赖安装以及独立 worker 的实际数量仍须满足；异构能力匹配已由[执行节点调度](v2-worker-scheduling.md)提供，公开部署的资源隔离继续单独完善。

## 图形、JSON 与并发编辑

图形配置和 JSON 可以双向切换。JSON 使用行号、高亮、格式化与校验，保存时始终做严格校验；布尔值、字符串数字、小数、未知字段和越界值不能成为额度。项目 JSON 示例：

```json
{"runtime": 1, "ai": null, "notification": null}
```

保存包含预期修订号。其他窗口已修改时，保留当前草稿，拒绝覆盖，并提供重新载入按钮。后台状态轮询不会覆盖未保存的配置。策略、修订历史和审计在同一事务提交；历史写入失败时额度也回滚。页面展示最近 50 次变更，完整历史仍在数据库。

平台管理员可以搜索、分页选择项目并修改其额度，只通过这个管理入口查看项目队列计数，不因此获得项目的模型或科学证据读取权。普通成员仅能查看已授权项目的额度和计数，不能修改平台策略。停用执行节点只停止领取新任务，并登记操作审计；不是立即杀死该进程。

## 数据库与部署升级

schema 23 增加部署策略、项目额度和变更历史三张小表，以及活跃任务索引，仍在原来的 PostgreSQL 中，不增加数据库或 MQ。领取任务和修改额度复用同一事务咨询锁；全局并发和项目占用在领取事务内检查，再通过租约代次维持单写入权。项目占用按当前队列一次汇总，不对大量排队任务反复读取整个历史。

升级时先停止旧 API／worker，执行 `threemind migrate` 后部署新版本，再启动工作站或服务。旧 worker 不理解数据库策略，不能在完成升级后混用。该阶段使用 schema 23；当前新增的能力匹配使用 schema 24，见[后续升级](v2-worker-scheduling.md)。独立 Runtime 无需这些表；模型格式与 419 项科学字段没有变化，不扫描或迁移旧 data。
