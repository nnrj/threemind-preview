# 时间帧传输与流量控制

[中文](temporal-frame-transport.md) | [English](../en/temporal-frame-transport.md)

## 为什么需要它

一个载体并不必然等于一个认知事件。长文本、未来的音频缓冲区，或远程
传感器的突发输入，本身都具有先后顺序。若把它们全部压进同一个
`SensoryFrame`，就会错误地让所有已编码特征在同一次运行时跃迁中共同激活。
在明文字符实验中，这甚至会在一步内产生近乎完全的有向图；那是传输伪影，
而不是已学习关联的证据。

因此，ThreeMind 保留完整的载体记录，同时将其编码结果按因果顺序递送为一串帧。
这不是语义长度限制，也不会丢弃、摘要或采样输入。

## 输入传输

```text
外部载体
  -> 适配器编码为有序 SensoryFrame 流
  -> InputBus 信封与可持久化队列
  -> 调度到环境时序 epoch
  -> 每个帧单独触发一次 Core 跃迁，并保持顺序
```

每个被接收的载体都会获得一个 `envelope_id`。原始载体仅在外部刺激日志中
保存一次，并记录来源、适配器、帧数量和递送状态。之后每一个帧递送事件都会
记录其信封、帧序号、计划时序 epoch、全局序号和特征数量。因此可以审计地回答：
*什么到达了、它如何被分帧、运行时按什么顺序收到它？*

队列状态会写入模型包状态。在载体传输过程中保存模型包时，尚未递送的帧不会
丢失；恢复该包后会继续按原有顺序递送。

`GET /api/input-queue` 会公开当前运行时的队列 epoch、待递送帧数量和下一个
计划信封，但不会公开载体内容。对已挂载意识实例也可使用
`GET /api/consciousnesses/{consciousness_id}/input-queue` 查询同一视图。
载体传输期间，UI 的“观测”面板也会显示当前待递送帧数量与输入 epoch。

### 文本感官的默认值

内置文本感官公开两个适配器设置：

- **每个因果帧的字符数**：默认 `24` 个规范化字符；
- **帧之间的环境时序间隔**：默认 `1`。

它们决定的是时间分辨率，而不是可接收文本的多少。任意长度的载体都会完整保存，
其全部片段都会进入队列。减小帧宽度会使局部共激活更精细；增大帧宽度则是一次
显式的实验选择，意味着更宽的感官瞬间。

离线 CLI 也走同一条路径。例如：

```powershell
python -m threemind stimulate .\experiment.tmind "一段较长的载体" `
  --frame-characters 24 --inter-frame-epochs 1 --step 1
```

`stimulate` 会在保存模型包前递送完全部因果帧；`--step` 只会在整条流递送完后额外增加稳定化 epoch。它不会静默截断长载体。

环境、躯体过滤、内感受、AI、用户手动和远程感官帧都通过同一个队列。即使多个
帧在同一个环境 epoch 到期，它们仍会按照稳定的全局插入顺序逐个推进，绝不会被
合并。

## 输出传输

运行时的 `OutputBus` 仍然是完整的匿名观测边界。浏览器传输则是独立的应用层职责：

1. 实时 WebSocket 快照以 `snapshot_begin`、有序节点/边分块和
   `snapshot_end` 发送；
2. UI 在存储每个快照片段后确认；
3. 实时活动使用紧凑增量。若慢客户端落后，传输层会标记
   `resync_required`，再发送新的完整分块快照，而不是悄悄让客户端保留一张
   不完整拓扑图。

分块大小只约束单条网络消息，不是图规模、激活、传播或记忆的限制；完整投影中的
每一个节点和边仍然存在。

## 对实验的含义

- 比较实验时应保持相同的适配器分帧设置；
- 遗留的“未分帧载体”造成的大型单步图爆发，应视为协议混杂因素，而非关联证据；
- 将结构事件与载体关联时，应检查刺激日志和帧递送日志；
- 未来的图像/音频适配器应在适配器内定义自身的时间分段，而不是在 Core 内插入
  任意批处理规则。

这一机制在形式上类似网络中的分帧传输，但它不是把网络协议伪装成认知。它的目的
是在联想动力学开始之前，保留外部感官源原本已经具有的时间结构。
